# 意图识别文本分类项目 —— 学习说明文档

## 一、项目定位与学习目标

### 1.1 项目是什么？

本项目是一个**中文意图识别（文本分类）HTTP 服务**，模拟车载智能座舱场景：用户说一句话（如"帮我播放周杰伦的歌"），系统自动判断其意图属于 12 个类别中的哪一个。

项目最大特色：**在同一个 FastAPI 服务中集成了 4 种从简到繁的技术方案**，让你通过对比理解 NLP 文本分类的完整技术演进路线。

### 1.2 学完能收获什么？

| 收获 | 具体内容 |
|------|----------|
| Web 服务开发 | FastAPI 路由、Pydantic 数据校验、自动文档生成 |
| 传统 NLP | 正则匹配、jieba 分词、TF-IDF 向量化、SVM 分类 |
| 深度学习 | BERT 预训练模型、微调训练、PyTorch 推理 |
| 大模型应用 | Prompt 工程、Few-shot Learning、RAG 检索增强 |
| 工程化能力 | 模型服务化、日志系统、异常处理、压测方法 |

## 四、四种分类方案深度对比

### 4.1 总览对比表

| 维度 | 正则规则 | TF-IDF + SVM | BERT | LLM Prompt |
|------|----------|--------------|------|------------|
| **原理** | 关键词包含匹配 | 词频统计 + 线性分类器 | 预训练语言模型微调 | 大模型 + 动态 Few-shot |
| **精度** | ~70% | ~80% | ~95% | ~95% |
| **速度** | 极快（μs） | 快（~2ms） | 中（~40ms） | 慢（~400ms） |
| **需要训练** | 否 | 是 | 是 | 否（需检索） |
| **需要 GPU** | 否 | 否 | 推荐 | 否（云端） |
| **泛化能力** | 极差 | 一般 | 好 | 好 |
| **适用场景** | 兜底/快速过滤 | 资源受限 | 生产主力 | 冷启动/标注辅助 |

### 4.2 各方案核心逻辑

**方案1：正则规则**
```
输入文本 → 遍历预编译正则 → findall 匹配关键词 → 命中则归类，否则 Other
```
- 优点：零延迟、无需训练
- 缺点：只能识别包含固定关键词的句子

**方案2：TF-IDF + SVM**
```
输入文本 → jieba分词 → 去停用词 → TF-IDF向量化 → SVM预测 → 类别标签
```
- 优点：轻量、快速、可解释
- 缺点：依赖分词质量，对语义理解有限

**方案3：BERT**
```
输入文本 → Tokenizer编码 → BERT前向推理 → logits → argmax → 类别名
```
- 优点：理解语义上下文，精度高
- 缺点：需要 GPU、模型体积大

**方案4：LLM + Few-shot**
```
输入文本 → TF-IDF相似度检索Top10 → 拼装动态Prompt → 调用LLM API → 解析结果
```
- 优点：无需训练、泛化强、可处理新意图
- 缺点：依赖网络、有 API 成本、延迟高

## 五、请求处理全流程

### 5.1 统一处理模式

所有 4 个接口遵循完全相同的代码模式：

```python
@app.post("/v1/text-cls/xxx")
def xxx_classify(req: TextClassifyRequest) -> TextClassifyResponse:
    start_time = time.time()                    # ① 计时开始
    response = TextClassifyResponse(...)        # ② 初始化空壳响应
    logger.info(...)                            # ③ 记录日志
    try:
        response.classify_result = model_for_xxx(req.request_text)  # ④ 推理
        response.error_msg = "ok"               # ⑤ 成功标记
    except Exception:
        response.error_msg = traceback.format_exc()  # ⑥ 异常兜底
    response.classify_time = time.time() - start_time  # ⑦ 计算耗时
    return response                             # ⑧ 自动序列化返回
```

### 5.2 关键设计思想

1. **Pydantic 数据契约**：请求/响应强类型定义，自动校验 + 自动文档
2. **模型预加载**：所有模型在 `import` 时一次性加载到内存，请求时零 IO
3. **全局异常兜底**：try/except 保证单次失败不影响服务存活
4. **耗时埋点**：每次请求记录推理时间，便于性能监控
5. **统一接口多模型并存**：通过 URL 路径区分，方便 A/B 对比

**核心知识点**：

### 第 4 阶段：TF-IDF + SVM（1小时）

**目标**：掌握经典机器学习文本分类全流程

**学习文件**：`training_code/train_tfidf.py` → `model/tfidf_ml.py`

**核心知识点**：
- **训练阶段**：分词 → 去停用词 → TfidfVectorizer.fit_transform → LinearSVC.fit → dump 保存
- **推理阶段**：load 加载 → 分词 → 去停用词 → transform → predict
- `fit_transform` vs `transform` 的区别（训练 vs 推理）

**动手练习**：
```bash
python training_code/train_tfidf.py
# 观察 assets/weights/tfidf_ml.pkl 是否生成
```

---

### 第 5 阶段：BERT 深度学习（2小时）

**目标**：理解预训练语言模型的微调与推理

**学习文件**：`training_code/train_bert.py` → `model/bert.py`

**核心知识点**：
- **预训练 + 微调** 范式：bert-base-chinese → 加分类头 → 在标注数据上训练
- `BertForSequenceClassification`：BERT + 线性分类层
- `Trainer` API：封装了训练循环、评估、保存
- 推理时 `model.eval()` + `torch.no_grad()` 关闭梯度节省内存
- `argmax(logits)` 取概率最大的类别

**关键参数**：
| 参数 | 含义 |
|------|------|
| `num_labels=12` | 12 分类任务 |
| `max_length=64` | 输入最大 token 数 |
| `batch_size=16` | 每批处理 16 条 |
| `num_train_epochs=4` | 训练 4 轮 |
| `warmup_steps=500` | 学习率预热 |

---

### 第 6 阶段：LLM + Few-shot（1小时）

**目标**：掌握大模型在分类任务中的工程化应用

**学习文件**：`model/prompt.py`

**核心知识点**：
- **动态 Few-shot**：不是固定示例，而是根据输入实时检索最相似的 10 条训练样本
- **RAG 思想**：TF-IDF 相似度 = 简化版向量检索
- **Prompt 模板**：`待选类别 + 参考例子 + 待识别文本` 三段式
- `temperature=0`：关闭随机性，保证输出确定
- OpenAI SDK 兼容接口：可对接任何兼容 OpenAI 格式的服务

**思考题**：为什么用 TF-IDF 相似度而不是直接让 LLM 分类？（提示：精度 + 稳定性）

## 九、面试高频问题

| 问题 | 回答要点 |
|------|----------|
| 为什么同时实现 4 种方案？ | 不同场景不同选择：正则兜底、TF-IDF 轻量、BERT 主力、LLM 冷启动 |
| TF-IDF 为什么要分词和去停用词？ | 中文无空格需分词；停用词（的、了、是）对分类无贡献反而引入噪声 |
| BERT 比 TF-IDF 好在哪？ | BERT 理解上下文语义，"苹果好吃"和"苹果手机"能区分 |
| Few-shot 为什么用动态检索？ | 固定示例可能误导；动态检索给 LLM 最相关的参考，提升准确率 |
| 推理延迟超标怎么优化？ | 模型蒸馏/量化、ONNX Runtime、GPU 加速、批处理 |
| 服务如何保证高可用？ | 异常兜底不崩溃、模型预加载避免 IO、多 worker 部署 |
